Shopify MCP — Architecture & Security

How the read-only Shopify assistant for Claude is built: the stack, the request flow, the authentication model, and the security decisions behind it. Reference doc, built 15 Jun 2026.

Cloudflare Workers MCP (Streamable HTTP) Shopify Admin GraphQL Read-only

1 Purpose

Give selected team members (e.g. sales) read-only access to Gym and Fitness and Revel Shopify data from inside Claude — products and orders — without ever handing them a Shopify API key, and with the API key fully managed centrally. The design goal: scoped, revocable, auditable access where the credential lives server-side and the exposed surface is deliberately smaller than the credential's own permissions.

The Worker is the only component that holds a Shopify credential. The client authenticates to the Worker with its own per-user token; the Worker then talks to Shopify with a store credential the user never sees. Two independent trust boundaries, joined in the middle.

Request lifecycle

  • 1. Inbound — Claude POSTs a JSON-RPC message to the Worker. The user's token arrives either as Authorization: Bearer <token> or embedded in the URL path (/c/<token>).
  • 2. Authenticate — Worker resolves the token against the USER_TOKENS map → { name, stores[] }. Unknown/missing token → 401.
  • 3. Dispatch — initialize / tools/list answered locally; tools/call checks the requested store is in the user's allowlist, then runs the handler.
  • 4. Mint & cache — handler fetches a Shopify token for that store via client_credentials (cached in-isolate ~20h of its 24h life), then calls the Admin GraphQL API.
  • 5. Shape & return — the response is reduced to a clean, PII-free object and returned as MCP tool content.

5 Authentication model

Two boundaries

  • User → Worker. Each person gets a unique random token, stored as a key in the USER_TOKENS secret (a JSON map). The value records their display name and which stores they may reach.
  • Worker → Shopify. Per-store client_id/client_secret live as encrypted Worker secrets. The Worker mints short-lived shpat_ tokens on demand. No Shopify credential is ever sent to the client.

Why two token-delivery methods

claude.ai's custom-connector UI (confirmed June 2026) accepts only OAuth or no-auth — it cannot send a custom Authorization header. So the Worker also accepts the token as a capability URL (/c/<token>): the user pastes one URL, leaves OAuth blank, and the path segment is the credential. Claude Code and desktop config files use the cleaner bearer header.

// USER_TOKENS secret — bearer -> identity + store allowlist
{
  "<random-token>": { "name": "Sales - Jane", "stores": ["gaf","revel"] }
}

// Connect (claude.ai / desktop GUI): paste as the connector URL
https://shopify-mcp.<account>.workers.dev/c/<token>

// Connect (Claude Code)
claude mcp add --transport http shopify \
  https://shopify-mcp.<account>.workers.dev \
  --header "Authorization: Bearer <token>"
Revocation. Remove a user's entry from USER_TOKENS and redeploy the secret — instant cutoff, no Shopify change. Adding a user is the inverse. Locking someone to one store is "stores":["gaf"].

6 Security model

Defense in depth — the key idea

The Shopify custom apps currently carry broad read scopes (including customer data) — a deliberate, accepted trade-off. Because of that, the Shopify scopes are not relied on as the boundary. The real containment is enforced in the Worker:

  • Tool whitelist. Only four read tools exist. There is no write path and no generic "run any query" tool, so the broad token cannot be driven beyond products/orders.
  • PII stripping. Order responses are explicitly shaped to exclude customer name, email, phone and addresses — even though the token could read them. Verified on live orders.
  • Per-store gate. Every tools/call checks the requested store against the user's allowlist before any upstream call.

Credential handling

  • Shopify client_id/secret and the USER_TOKENS map are Cloudflare Worker secrets — encrypted at rest, never in source.
  • Nothing secret is committed. Worker code and config are clean; local creds live in chmod 600 files outside the git repo; the public docs use placeholders only.
  • Minted shpat_ tokens are short-lived (24h) and never leave the Worker.

Residual risks (accepted / known)

  • Capability URL = bearer in a URL. Anyone holding the link has that user's access, so it is treated as a secret and is per-user revocable. Suitable for read-only, non-PII data.
  • Broad Shopify scopes. If the Worker were ever misconfigured to expose more, the token's ceiling is high. Mitigated by the small, audited tool surface.
  • No rate limiting / audit log yet (see next section).

7 Operations

Source lives in the vault at Agent/Scripts/shopify-mcp/ (worker.js, wrangler.toml, README.md). Deploy and secret management via Wrangler:

# deploy
cd Agent/Scripts/shopify-mcp
export $(grep -v '^#' ~/.cloudflare-env | xargs)
npx wrangler@latest deploy

# set / rotate a secret (reads from local chmod-600 creds files)
echo -n "$CLIENT_SECRET" | npx wrangler@latest secret put GAF_CLIENT_SECRET

# add or revoke a user = edit the USER_TOKENS JSON, re-put
echo -n '{...}' | npx wrangler@latest secret put USER_TOKENS

8 Future enhancements

  • OAuth 2.0 on the Worker → native, header-free connector auth in the claude.ai UI (replaces the capability URL).
  • Cloudflare Access in front → staff log in with their @gymandfitness.com.au Google account instead of a per-user token.
  • Trim Shopify scopes to read_products + read_orders so the credential ceiling matches the exposed surface.
  • Audit logging (who called what, when) and rate limiting per user.
  • KV-backed token cache for token reuse across Worker isolates.
